# M2: durable processing and recovery

Validated 2026-09-09: **31 tests passed** in the isolated Linux Compose environment, with Ruff and strict mypy passing. No integration tests were skipped.

- Two workers raced 100 duplicate processing calls; one attempt committed two exact financial observations.
- Lease heartbeat, expiry and takeover tests reject stale owners and never revive expired leases.
- Real child processes were killed before SQL commit and after commit/before acknowledgement. Uncommitted writes disappeared; committed effects were not repeated.
- Outbox double-publication and complete removal of the isolated test Redis stream recover from authoritative SQL jobs.
- Retry schedules, bounded attempt exhaustion, request-key conflicts and linked DLQ redrive retain history.
- `python scripts/service_drills.py` stopped the isolated PostgreSQL container. The delivery remained pending with no acknowledgement; after restart the leased job recovered and its prior attempt remained visible.
- The same drill restarted SeaweedFS and verified the original manifest/checksum/body survived.

Commands:

```text
docker compose -p secrecon-test -f compose.yaml -f compose.test.yaml run --build --rm test
python scripts/service_drills.py
```

The drill hard-codes the `secrecon-test` Compose project. It cannot target the local application project through an argument. Every test job and isolated stream has a unique identifier; unrelated local projects are untouched.

Owner demonstration: `secrecon jobs list`, `secrecon jobs show <id>`, and `secrecon jobs redrive <id>`. The worker prepares inputs outside a transaction, then checks its SQL lease and token before and after committing derived effects. Redis acknowledgement follows durable state, never precedes it.
