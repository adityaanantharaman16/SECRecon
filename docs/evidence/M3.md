# M3: incremental ingestion, backfills and offline replay

Validated 2026-09-10 in the isolated Linux Compose environment: **48 tests pass**, no integration tests skipped. Ruff, formatting and strict mypy pass. Domain/job correctness coverage is **89.47%** against the enforced 80% gate. The installed dependency audit reports no known vulnerabilities; the local editable project is excluded from advisory lookup.

Verified behavior:

- SQL watchlist polling catches up after a gap, retains an overlap and prevents duplicate scheduling.
- An interrupted multi-page backfill resumes from durable state. Historical pages and children commit together; overlapping requests preserve exactly two distinct synthetic financial assertions.
- Submissions can precede available facts; later snapshots fill coverage without changing the original records.
- Cancellation blocks a claimed discovery's final scheduling transaction while preserving its raw source.
- Four concurrent callers share the two-request/second Redis budget; Redis unavailability fails closed.
- Inventory repairs missing SQL source registration and normalization notifications idempotently.
- Replay into an isolated generation is deterministic even with reversed original processing order and with HTTP calls forbidden.
- Replay into a physically empty, newly migrated PostgreSQL database reconstructs financial rows and provenance. It does not fabricate old jobs or attempts.
- Replay resumes after interruption. Corruption and mismatched expected digests block promotion. New ingestion follows the newly active generation; the previous generation remains intact.
- The combined suite includes M2's real worker-process termination cases. The separate database-outage and S3-restart drill also passed under M2.

Primary command:

```text
docker compose -p secrecon-test -f compose.yaml -f compose.test.yaml run --build --rm test
```

Runtime and test images are separated: the application image uses locked production dependencies and a non-root user; the test image adds lint/type/test tools. Host bytecode caches are excluded from container builds. Default SEC mode remains offline.

The production stack also passes `docker compose up -d --build`. The documented synthetic seed loads one company, two filings and two exact decimal assertions. HTTP liveness/readiness and fact/provenance queries succeed against the running API at schema 0004.

The committed milestone (`d1c51a7`) was independently verified in a fresh local clone with new configuration and isolated service volumes: all 48 tests passed in 24.56 seconds, with the same 89.47% coverage. See M0 evidence for the exact clone and Compose commands.

During validation, retained test jobs exposed a first-batch assumption in a queue recovery test; the probe now has explicit priority and reads bounded batches. The original coverage measurement was 79%; additional worker failure, heartbeat and acknowledgement tests raised it to 89.47% without lowering the gate.

Environment repair: Docker Desktop encountered inaccessible stale Windows socket files after the session resumed. The socket runtime directories were preserved under timestamped `secrecon-recovery` names and recreated. Images, volumes and settings were not reset. The backend returned to healthy operation. This was a host tooling issue, not a SECRecon database failure.
