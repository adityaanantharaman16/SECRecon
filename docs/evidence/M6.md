# M6: failure and performance evidence

## M6.1 completion status

The fixture-driven isolated failure harness and its real-service acceptance gate completed on 2026-09-22. M6.2 performance baselines and M6.3 recovery reporting remain separate later slices, so M6 as a whole remains in progress.

Implemented:

- `scripts/service_drills.py` accepts only base names matching `secrecon-drill-<short-unique-name>`, generates a fresh child project name for every run, proves that no labeled containers/volumes/networks already use that child name before claiming cleanup ownership, always supplies `-p` plus `compose.yaml` and `compose.test.yaml`, and rejects the development, release and ordinary test project names before invoking Docker.
- The database-outage/object-store-restart scenario is defined by `tests/fixtures/failure_drills/database_outage.json`.
- Each run creates a fresh drill key, records Git/Docker/Compose/Python versions and Docker CPU/memory/OS/architecture, starts only the isolated test stack, captures before/after authoritative SQL job, attempt, event and outbox invariants, checks Redis acknowledgement state and immutable source bytes, validates every attempt span against the persisted job trace context, waits boundedly for object storage after startup/restart, bounds all subprocess waits, records successful/failed/timed-out command outputs/return codes/timings plus total duration, writes a JSON report under ignored `.local/failure-drills/`, and removes only the child project it established as unused.
- `--runs 3` provides the required consecutive-run gate without weakening cleanup or isolation between runs.

No job-ownership, comparison, projection, archive or telemetry semantics changed. The harness reuses the existing SQL store, transactional outbox, queue, worker, fenced lease recovery, archive and OpenTelemetry context propagation described by ADRs 0002–0004.

## M6.2 performance baseline

### Harness

- `scripts/performance_baseline.py` (host) accepts only `secrecon-perf-<short-unique-name>` base names. It reuses the M6.1 isolation primitives extracted from `scripts/service_drills.py` (`validate_isolated_project`, `IsolatedCompose`): a fresh child project per run, a proof that the child has no labeled resources before cleanup ownership is claimed, a pinned `compose.yaml` + `compose.test.yaml`, and removal of only that child. `secrecon`, `secrecon-test`, `secrecon-drill-*` and every other name are refused before Docker runs (exit 2).
- `scripts/performance_probe.py` (inside the isolated `test` container) runs each phase with the production `Worker`, `Dispatcher`/transactional outbox, Redis Streams queue, fenced SQL leases, archive, `replay.rebuild` and API. It does not add a scheduler and does not bypass generation or lease locks. The four-worker benchmark is queue reprocessing: normalize jobs for a new generation, drained by 4 worker processes. It is distinct from the serialized `secrecon replay` command, which is measured separately as the `rebuild` baseline.
- The dataset is frozen as `synthetic-perf-v1`: 100 synthetic companies (CIKs `0990000000`+) × 10 filings × 100 observations = **100,000 observations in 1,000 filing-shaped sources** plus 100 submissions sources. 100 extra deliveries (10% of filings) are spread evenly, giving 1,200 jobs. Hosts use `synthetic.invalid`, so this is never SEC data. The dataset fingerprint is recorded per run.
- Correctness for replay: 1-worker, 4-worker and sequential-rebuild digests must be equal, **and** an independent row-level `EXCEPT ALL` multiset comparison of companies, filings, facts, fact_provenance, filing_sources and amendment links must show zero differing rows. Every job must be `succeeded`, with one processing run per unique source.
- Recovery is judged from SQL per ADR 0002. A production worker holding the lease is SIGKILLed inside the fenced commit, before any projection write. The victim attempt must end `lease_expired` (token 1) and the rescuer's must be `succeeded` (token 2), with exactly one processing run and the source's 100 facts and provenance rows. Remaining Redis deliveries are reported, not gated.
- Reads use an open-loop fixed-rate schedule. Latency is measured from each request's scheduled send time, so client queueing is not hidden. The load rotates over 10 indexed list/detail routes at `limit=100` against a single uvicorn API process. Cold reads start after a PostgreSQL restart plus a fresh API process; warm reads follow. `EXPLAIN ANALYZE` plans are captured after timing.
- The soak runs fixed-rate arrivals at 50% of the measured four-worker rate. Each full cycle writes a fresh generation, and worker telemetry exports to an unresponsive collector. The leak rule was pre-declared before any run: after a 120 s warm-up, the late-third maximum of each series may exceed its early-third maximum by at most 10% plus a per-metric absolute tolerance. Telemetry export queues are fixed-capacity by construction and are gated on their hard capacity instead.
- Full reports are ignored machine-local artifacts under `.local/performance/`. `scripts/performance_summary.py` produces allowlisted, credential-checked summaries, committed under [performance/](performance/) with the source report's SHA-256.

Harness bugs found by real runs, each fixed with a regression test before the timed runs:
- The seed phase omitted its subcommand.
- The `compare` phase did not exist.
- Recovery processed a source from a different dataset spec, so its fact-count check failed; the first smoke run reported `CORRECTNESS FAIL`.
- A telemetry queue filling to its fixed capacity was misread as a leak.

Supporting report values:
- The digest `9be5c25b…d16ae` is identical for 1-worker, 4-worker and rebuild. `EXCEPT ALL` found 0 differing rows in every table (100,000 facts, 100,000 provenance rows, 1,000 filings, 100 companies, 2,000 filing sources). All 1,200 jobs succeeded, with 1,100 processing runs.
- Sequential `replay.rebuild` took 83.5 s (1,197.7 observations/s).
- Recovery: the victim was killed with 59.96 s of lease remaining, the lease was reclaimed after 60.75 s, and the job succeeded at 61.0 s in all three trials. Each trial showed `lease_expired`→`succeeded`, tokens 1→2, 1 processing run and 100 facts.
- Soak: 20 complete cycles; every cycle digest equals the replay digest. Per-5-minute p95 enqueue-to-success was 2.01–2.06 s with no upward trend, and the backlog drained 1.551 s after arrivals stopped. At the end: 0 open jobs, 0 unsent outbox rows, 0 Redis pending entries, 5 PostgreSQL connections.
- Open jobs, outbox, Redis stream/pending/memory, PostgreSQL connections, dispatcher RSS, worker RSS/threads/pool and Redis/object-store container memory were all bounded. Telemetry queues stayed at or below their capacity of 256, dropping 8,852–10,133 trace records per worker against the hung collector, as designed.
- The **only** unbounded series was `container.postgres.memory_bytes` from `docker stats`: early max 312 MiB, late max 648 MiB. Over the same period the database grew to 4.54 GB, because every soak cycle writes a fresh 100,000-fact generation.

Bottleneck: the replay is CPU-bound on this 2-vCPU host. During the four-worker replay the test container (workers) averaged 114% CPU and PostgreSQL averaged 69%, on only 200% available. The four-worker speedup over one worker is 1.62×, and the dispatcher ceiling of 50 jobs/s was not reached (23.65 jobs/s). The slowest read shape is `facts-by-cik-period` (p95 ≈ 20 ms). Its plan uses `facts_period_page` and then filters on `cik`, discarding 8,512 rows. It is the first index candidate if read load grows, but it was not tuned because the p95 target is met with about 15× headroom.

Optional discovery-to-normalized lag (item 5) is **out of scope** for this fixture-only slice. It needs live upstream discovery, and SEC acceptance-to-discovery delay cannot be measured honestly with fixtures. The soak's enqueue-to-success p95 of about 2 s is application-side processing lag only and is not reported as discovery lag.

### M6.2 status: in progress, not complete

- Replay throughput with digest equivalence, read latency and crash recovery met their targets in run 1, with correctness intact.
- The soak **missed** its pre-declared bounded-growth target on one series, PostgreSQL container memory. The working explanation is file-backed page cache and shared buffers tracking a database that grows by design (a fresh generation every cycle). This is **not yet proven**, so no revised target is proposed yet.
- Guide-sized run 2 was started from committed harness `886d177`, with a clean image-input tree recorded in the report. It additionally samples reported-only cgroup `memory.stat` (anon/shmem/active_file/file) for PostgreSQL, Redis and the object store. Its result, and any evidence-backed explanation plus revised soak rule, will be recorded here before M6.2 is claimed.
- The full isolated test gate has not yet been recorded for this branch.
