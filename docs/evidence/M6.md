## M6.2 performance baseline

### Harness

- `scripts/performance_baseline.py` (host) accepts only `secrecon-perf-<short-unique-name>` base names. It reuses the M6.1 isolation primitives extracted from `scripts/service_drills.py` (`validate_isolated_project`, `IsolatedCompose`): a fresh child project per run, a proof that the child has no labeled resources before cleanup ownership is claimed, a pinned `compose.yaml` + `compose.test.yaml`, and removal of only that child. `secrecon`, `secrecon-test`, `secrecon-drill-*` and every other name are refused before Docker runs (exit 2).
- `scripts/performance_probe.py` (inside the isolated `test` container) runs each phase with the production `Worker`, `Dispatcher`/transactional outbox, Redis Streams queue, fenced SQL leases, archive, `replay.rebuild` and API. It does not add a scheduler and does not bypass generation or lease locks. The four-worker benchmark is queue reprocessing: normalize jobs for a new generation, drained by 4 worker processes. It is distinct from the serialized `secrecon replay` command, which is measured separately as the `rebuild` baseline.
- The dataset is frozen as `synthetic-perf-v1`: 100 synthetic companies (CIKs `0990000000`+) × 10 filings × 100 observations = **100,000 observations in 1,000 filing-shaped sources** plus 100 submissions sources. 100 extra deliveries (10% of filings) are spread evenly, giving 1,200 jobs. Hosts use `synthetic.invalid`, so this is never SEC data. The dataset fingerprint is recorded per run.
- Correctness for replay: 1-worker, 4-worker and sequential-rebuild digests must be equal, **and** an independent row-level `EXCEPT ALL` multiset comparison of companies, filings, facts, fact_provenance, filing_sources and amendment links must show zero differing rows. Every job must be `succeeded`, with one processing run per unique source.
- Recovery is judged from SQL per ADR 0002. A production worker holding the lease is SIGKILLed inside the fenced commit, before any projection write. The victim attempt must end `lease_expired` (token 1) and the rescuer's must be `succeeded` (token 2), with exactly one processing run and the source's 100 facts and provenance rows. Remaining Redis deliveries are reported, not gated.
- Reads use an open-loop fixed-rate schedule. Latency is measured from each request's scheduled send time, so client queueing is not hidden. The load rotates over 10 indexed list/detail routes at `limit=100` against a single uvicorn API process. Cold reads start after a PostgreSQL restart plus a fresh API process; warm reads follow. `EXPLAIN ANALYZE` plans are captured after timing.
- The soak runs fixed-rate arrivals at 50% of the measured four-worker rate. Each full cycle writes a fresh generation, and worker telemetry exports to an unresponsive collector. The leak rule was pre-declared before any run: after a 120 s warm-up, the late-third maximum of each series may exceed its early-third maximum by at most 10% plus a per-metric absolute tolerance. Telemetry export queues are fixed-capacity by construction and are gated on their hard capacity instead.
- Full reports are ignored machine-local artifacts under `.local/performance/`. `scripts/performance_summary.py` produces allowlisted, credential-checked summaries, committed under [performance/](performance/) with the source report's SHA-256.
- Load driver: the guide lists Locust as the planned load tool. The probe instead uses the existing `httpx` runtime dependency with its own open-loop scheduler. This adds no dependency, runs inside the isolated `test` container, and measures latency from each request's *scheduled* time. A closed-loop driver would slow its request rate when the server slows, which hides queueing delay (coordinated omission).

Harness bugs found by real runs, each fixed with a regression test before the timed runs:
- The seed phase omitted its subcommand.
- The `compare` phase did not exist.
- Recovery processed a source from a different dataset spec, so its fact-count check failed; the first smoke run reported `CORRECTNESS FAIL`.
- A telemetry queue filling to its fixed capacity was misread as a leak.

### Soak memory miss: evidence-backed explanation

The only unbounded series in both runs was `container.postgres.memory_bytes` from `docker stats`. In run 2 its early-third max was 251 MiB and its late-third max 354 MiB, against a limit of 308 MiB (10% + 32 MiB). Run 2's reported-only cgroup v2 `memory.stat` sampling splits that figure.
- The `anon`, `shmem`, `active_file` and `file` rows are in the committed summary under `verdicts[3].details.diagnostics_not_gated`. There the harness applies 10% + 16 MiB.
- The `kernel` and `docker stats` rows, and the residual, were computed from the ignored raw report with a read-only post-hoc script. It reuses the harness's `growth()` window rule at 10% + 32 MiB.
- Every "bounded" row below is bounded under either tolerance.

| PostgreSQL container series (MiB, 103 samples, 120 s warm-up excluded) | early median | late median | early max | late max | early/late rule |
| --- | ---: | ---: | ---: | ---: | --- |
| `anon` (process heap/private memory) | 17.7 | 17.8 | 31.5 | 28.2 | bounded |
| `shmem` (`shared_buffers`) | 140.4 | 140.6 | 140.4 | 140.6 | bounded |
| `active_file` (page cache marked active) | 0.0 | 93.4 | 25.6 | 103.9 | grows |
| `file` (all page cache) | — | — | 2,268 | 2,349 | bounded |
| `kernel` | 40.9 | 70.9 | 68.2 | 73.3 | bounded |
| `docker stats` usage | 198.4 | 322.3 | 251.0 | 354.3 | grows |

Across every sample, `docker stats` usage minus (`anon` + `shmem` + `kernel` + `active_file`) has a median of −0.5 MiB (range −10.5 to +27.2 MiB). On this cgroup-v2 host, the Docker figure is therefore almost exactly those four parts. Docker subtracts only *inactive* file cache.

Conclusion: PostgreSQL's process memory and shared buffers were flat for 30 minutes. All of the growth is `active_file`, which is reclaimable, file-backed kernel page cache over the database's own data files. The database grew from 0.59 GB to 4.61 GB during the soak because every cycle deliberately writes a fresh 100,000-fact generation. Page cache over newly written and re-read pages, for example digest and verification reads, is promoted to the kernel's active list. That mechanism is inferred from standard Linux LRU behaviour and was not traced page by page. The measured fact is that `active_file`, not process or shared memory, carries the growth. This is a flaw in the memory probe, not evidence of a leak in SECRecon's queue, connection, worker or telemetry paths.

What is *not* claimed:
- This does not prove page cache would stay bounded if the database were allowed to grow indefinitely. It is reclaimable under memory pressure, and no container limit was set to exercise that.
- The recorded verdict stays **TARGET MISSED**. The explanation has not been used to rewrite the run's gate after the fact.

**Proposed revised soak memory rule**, for review:
- For stateful containers, gate `cgroup anon + shmem` with the same pre-declared early/late rule and tolerances. In this run that was 171.8 → 168.8 MiB, bounded.
- Report `docker stats` usage and `active_file`/`file` alongside, normalised to database size, as non-gated context.
- Process RSS remains gated for workers, the dispatcher and the API.

A follow-up change to `soak_verdict` and a fresh guide-sized run would be needed before the soak can be reported as met. That change, and M6.3's final benchmark report, are left to review rather than folded into this slice.
