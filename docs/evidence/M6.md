# M6: failure and performance evidence

## M6.1 completion status

The fixture-driven isolated failure harness and its real-service acceptance gate completed on 2026-09-22. M6.2 performance baselines and M6.3 recovery reporting remain separate later slices, so M6 as a whole remains in progress.

Implemented:

- `scripts/service_drills.py` accepts only base names matching `secrecon-drill-<short-unique-name>`, generates a fresh child project name for every run, proves that no labeled containers/volumes/networks already use that child name before claiming cleanup ownership, always supplies `-p` plus `compose.yaml` and `compose.test.yaml`, and rejects the development, release and ordinary test project names before invoking Docker.
- The database-outage/object-store-restart scenario is defined by `tests/fixtures/failure_drills/database_outage.json`.
- Each run creates a fresh drill key, records Git/Docker/Compose/Python versions and Docker CPU/memory/OS/architecture, starts only the isolated test stack, captures before/after authoritative SQL job, attempt, event and outbox invariants, checks Redis acknowledgement state and immutable source bytes, validates every attempt span against the persisted job trace context, waits boundedly for object storage after startup/restart, bounds all subprocess waits, records successful/failed/timed-out command outputs/return codes/timings plus total duration, writes a JSON report under ignored `.local/failure-drills/`, and removes only the child project it established as unused.
- `--runs 3` provides the required consecutive-run gate without weakening cleanup or isolation between runs.

No job-ownership, comparison, projection, archive or telemetry semantics changed. The harness reuses the existing SQL store, transactional outbox, queue, worker, fenced lease recovery, archive and OpenTelemetry context propagation described by ADRs 0002–0004.
